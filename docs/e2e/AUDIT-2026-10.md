# Static audit of 2026-10: findings and fixes

An external static audit of commit `39e7a55` reported eight findings against
the E2E add-on (`tools/icq-e2e`, Rust) and the key directory
(`server/e2e`, Go). This document gives, for each one, the verdict after
checking the code, what was changed, and the regression tests. Each new test
was run against the old logic (the fix temporarily reverted) and failed
there; it passes with the fix.

| 2 | An Olm message is tried against every device's session | confirmed | `keys.rs`, `crypto.rs` |
| 3 | A first message over the fallback key can be replayed | confirmed | `keys.rs`, `crypto.rs`, `store.rs` |
| 4 | A key log that breaks after it was trusted means "no constraints" | confirmed | `kt.rs`, `crypto.rs`, `keys.rs` |

## 1. A panic in a hook sends or hands over the original bytes

**Verdict: confirmed.** `hook_send` ran the rewriting `send` under
`catch_unwind` and, on a panic, called the original `send` with the client's
own buffer - in encrypt mode the plaintext of the message, and on a socket
with TLS to the server, past the TLS. `hook_recv` did the same the other way:
on a panic it called the original `recv` straight into the client's buffer,
handing over undecrypted containers or raw TLS records. `tls_gate` let the
call go on after a panic, which skipped the check that refuses a socket for
good. In `hook_calls.rs`, `keyed_socket` answered "not an agreed call" after a
panic, so the media of an agreed call could go out plain through
`WSASendTo`, and an inbound datagram reached the client undecrypted.

The file transfer hooks (`hook_files.rs`) already fail closed (a panic marks
the pipe broken, shuts the socket and answers `WSAECONNRESET`); the TLS pump's
`catch_unwind` passes no data; the observe-mode paths only look at bytes that
already went through.

**Fix.** A new `fail_closed` in `hook.rs`: in every mode but observe (which
never has TLS), a panic in the `send` or `recv` body, or in `tls_gate`, fails
the call with `SOCKET_ERROR` / `WSAECONNRESET`, sets the socket's `blocked`
flag so every later call on it fails the same way (`tlsio::blocked` checks it
first), logs why and queues a note for the chat ("The connection was closed:
the add-on hit an internal error ... nothing is sent or shown unprotected").
The client reconnects on a fresh socket. Observe mode keeps passing through.
`keyed_socket` now counts a socket as an agreed call's after a panic whenever
`keyed_after_panic` cannot rule it out, so its media takes the encrypted path,
which drops what it cannot handle.

**Tests** (`hook.rs`, `socket_tests`, over a real loopback socket with a
panic injected into the body):

- `a_panic_in_send_sends_nothing_and_the_socket_stays_refused`
- `a_panic_in_recv_hands_over_nothing_and_the_socket_stays_refused`

## 2. An Olm message is tried against every device's session

**Verdict: confirmed.** `OwnKeys::decrypt_olm` tried every session held for
the peer, whichever device it was with, and the caller stored the advanced
ratchet under the `sender_device` the container named. A message naming one
device therefore opened under another device's session - a revoked device's
among them - and that session's state was then filed under the wrong device.
Revoked devices kept their sessions for good.

**Fix.** `decrypt_olm` tries only `sessions[peer][sender_device]`; a pre-key
message may still make a new session for that device after the directory
check, as before. Devices the directory marks revoked are remembered in the
state file (`OwnKeys::revoked`) and nothing from them is read again, through
an old session or a new one. On every look at a contact
(`checked_contact`, i.e. every outgoing message and `/e2e status`) the
sessions with devices that are not active and signed in the directory are
dropped (`forget_inactive_devices`); after every sync of a trusted key log the
sessions with devices the log no longer shows are dropped
(`forget_devices_not_in_log`). The engine now syncs the log (at most once a
minute) on every inbound message, not only on pre-key ones, so this also
happens in a conversation that only receives.

**Limit.** With a server that keeps no key log, a conversation that only
receives drops a revoked device's session at the next outgoing message or
`/e2e status`, not before.

**Tests** (`keys.rs`):

- `only_the_session_of_the_device_a_message_names_is_tried` - session A with
  `sender_device` A is read; the same session with `sender_device` B is
  refused and nothing is stored.
- `a_revoked_devices_session_opens_nothing` - after the directory revokes A
  and the contact is looked at, A's session is gone, its next normal message
  and a fresh pre-key message are refused, and the refusal survives a
  restart.
- `a_device_gone_from_the_directory_loses_its_session`

## 3. A first message over the fallback key can be replayed

**Verdict: confirmed** (and reproduced on vodozemac 0.11.1). A one-time key is
used up by the session it opens; the fallback key is not. Replaying the first
pre-key message of a session made over the fallback key, after its ratchet had
moved on, failed in the existing session (the message key was spent) and then
`create_inbound_session` made a second, fresh session from it: the old message
was shown again as new, and the stored session was replaced by one rolled back
to the start of the conversation.

**Fix.**

- Before `create_inbound_session`, `pre.session_id()` is checked against a
  per-(peer, device) set of the inbound sessions accepted so far
  (`OwnKeys::inbound_ids`, in the state file); a repeat is refused. An id is
  recorded only once its message opened and passed the envelope checks, so a
  tampered container cannot burn it. Ids are kept for `INBOUND_ID_KEEP` = two
  fallback-key lifetimes (the key's own week and the week its private half is
  kept after a replacement) + the 14-day message age limit + one day = 29
  days.
- A fallback key that opened a session is marked used (`fallback_used`) -
  told apart from a one-time key by the account's stored one-time key count
  not changing - and is replaced at the next publish step (the poll every two
  seconds), not at the end of its week. The publisher now also rotates a due
  fallback key during a sign-on, and reports it as `Done` so the new key is
  saved. vodozemac keeps the replaced key's private half until the next
  replacement, so a message claimed just before the swap still opens.
- State version 3 (`store.rs`). The migration from version 2 records the id
  of every session the file holds as seen at the load, so the first messages
  of sessions made before this build cannot make them again either. A
  version-2 build refuses the file rather than dropping the set.

**Trade-off.** A genuine first message delivered twice (online and again from
the offline store) is shown once; the second copy is refused as a replay.

**Tests:**

- `keys::tests::a_replayed_first_message_over_the_fallback_key_is_refused_and_rolls_nothing_back`
  - the test the auditor asked for: a session over the fallback key (no
  one-time key published), the ratchet advanced both ways, then the first
  pre-key container through `decrypt()` again: refused, the stored session
  pickle and the account pickle unchanged, the next real message still opens,
  and the refusal survives a restart.
- `keys::tests::a_used_fallback_key_is_replaced_at_the_next_step`
- `keys::tests::inbound_session_ids_are_kept_long_enough_and_then_forgotten`
- `store::tests::a_version_two_state_remembers_the_sessions_it_holds`

## 4. A key log that breaks after it was trusted means "no constraints"

**Verdict: confirmed.** When the log was rewritten, signed by another key,
gone, or seen differently by an auditor (split view), the engine set
`LogStatus::Broken` for the sign-on only, and `Engine::log_check` returned
"no constraints" for every status but `Ok`. A server that broke its own log
was therefore handed exactly what the log exists to check: new contacts,
new devices and changed account keys were all trusted on first use from that
moment, and the next sign-on started without any memory of the break.

**Fix.** Three states are told apart (`kt::Trust`, `Engine::log_trust`):

- `NeverHadLog` - no log ever seen (an older server): trust on first use, as
  before;
- `Trusted` - the copy is up to date and adds up;
- `BrokenAfterTrust` - a log we had trusted (its key pinned or entries kept)
  broke. Stored in the state file (`LogState::broken`), sticky across
  sign-ons until `/e2e resetlog`, which clears it with the rest of the copy.
  The copy is frozen as last trusted and the server is not asked again.

While broken after trust, `log_check` never returns "no constraints"
(`frozen_log_check`): a contact whose account key was never pinned, and a
changed account key, are refused (the message is held with a note, never
sent in clear); a device is used only if a session with it already exists or
the frozen copy shows it with the same keys. Inbound, a new Olm session needs
the pinned account key and a device the frozen copy shows (`decrypt_olm`).
Sessions already made go on, so the user keeps their existing conversations.
A transient network failure (`LogStatus::Failed`) is unchanged.

**Tests** (`crypto.rs`):

- `a_log_broken_after_it_was_trusted_takes_nothing_new_until_resetlog` -
  replaces `a_rewritten_log_is_said_and_keys_fall_back_to_first_use`, which
  asserted the old behaviour: after a rewrite the existing contact still
  encrypts; a contact never checked is held, and its pre-key message is
  unreadable with no session made; a changed account key is held and not
  pinned; all of it holds after a restart; `/e2e resetlog` brings the new
  contact back.
- `a_log_the_auditor_never_saw_is_not_trusted` - updated: after a split view
  a contact never checked is held, not trusted on first use.
- `a_server_that_never_had_a_log_is_not_a_broken_one`

## 5. A message is let go before its ratchet step is saved

**Verdict: confirmed.** The state file was written after each frame, after
the rewritten bytes had already been released: an encrypted message went out,
and a decrypted one reached the client, whether or not the advanced state
reached the disk. After a failed save and a restart, the old state could send
another message under a message key already used, and a shown message's
ratchet step was lost.

**Fix.** The session gives its engine a way to write the state
(`Engine::set_persist`, over the session's `Store`). The engine calls it
before letting go of anything whose ratchet moved on:

- **outgoing** (messages, control messages, call and file key exchanges): if
  the save fails, the message is not sent, a note says so in the chat, and
  encryption with that contact waits until a save works (each later message
  tries the save first). The ratchet is not rolled back: an unsent ciphertext
  costs nothing, a reused key would.
- **incoming**: if the save fails, the decrypted message is dropped with a
  note, and the keys in memory are put back to what the disk has
  (`OwnKeys::snapshot` / `restore` for what decrypting may change), so the
  same message opens if it comes again.

**Trade-off.** A message dropped this way is not shown. If the sender sends it
again it opens; if it was an offline message and the client has already told
the server to delete its offline store, it is lost, and the note asks the
user to have it sent again. Holding it in memory instead would mean showing a
message whose ratchet step is not on disk, which is what the finding is about.

**Test:** `session::tests::a_message_is_let_go_only_once_its_state_is_on_disk`
- with the state file unwritable, an outgoing message is refused and the next
one waits too, an incoming message is not shown, and nothing is written;
once the disk takes it again, the same incoming message opens and messages go
out.

## 6. Two processes can use one state file

**Verdict: confirmed.** Nothing stopped two clients signed on as the same
account on one computer from each loading `<uin>.state`, advancing their own
copies and saving over each other: ratchets regressed, one-time keys were
spent twice, and a message key could be used twice.

**Fix.** `store::StateLock`: an exclusive lock (`File::try_lock`, i.e.
`LockFileEx`) on `<uin>.lock` next to the state, taken when the session opens
and held for its life; the operating system gives it up when the process ends,
however it ends. A session that cannot take it opens **locked out**
(`Session::locked_out`, `Engine::lock_out`): it never reads or writes the
state, announces no account key, publishes nothing, and holds every message
rather than sending it in clear - outgoing messages are refused with a note
("another ICQ signed on as ... is using its encryption keys"), incoming
containers are unreadable with a note, `/e2e` commands say why. The log says
it at sign-on.

**Limit.** A state file that cannot be read (corrupt, another Windows user's)
still turns encryption off, as before; only the lock case holds messages.

**Tests:**

- `session::tests::a_second_session_of_the_same_account_is_locked_out_and_holds_messages`
- `store::tests::the_state_lock_is_held_once_and_free_again_when_dropped`

## 7. Revoking a device needs only a token

**Verdict: confirmed.** `DELETE /e2e/v1/devices/{device_id}` needed a bearer
token and some account key announced on the token's BOS connection, any one.
The server - or anyone it issues a token to - could strip an account of its
devices, which also opens the way to a reset (a new account key without
proof).

**Fix.** The request now carries `{"issued_at", "signature"}`: the stored
account key's signature over the new `revoke` message (`RevokeMessage`:
`"revoke" | screen name | device id | issued_at`, 8 bytes big endian). The
server takes `issued_at` only within five minutes of its own clock either way
(`revokeWindow`) and each signature once (`usedSignatures`, kept while it can
still be valid). The bearer-token and announcement checks stay. Errors:
`400 bad_request` (no body), `400 invalid_signature` (missing, wrong key, other
device, account or time, outside the window), `409 replayed`.
`KEY-DIRECTORY-API.md` sections 3.3, 5, 6.5 and 7 describe it. The add-on has
no revoke call, so nothing there changes. A user who lost the account key
cannot sign a revoke: the owner revokes the old devices through the
management API (unchanged), after which the user can reset.

**Limit.** The set of used signatures is in memory: after a server restart a
captured revoke could be replayed within its five minutes - against a device
it already revoked, which is a no-op.

**Tests** (`server/e2e/handler_test.go`, table-driven, testify):

- `TestHandler_RevokeNeedsTheAccountKeysSignature` - no body, no signature,
  signed by a stranger, for another device, for another account, another
  time than signed, too old, from the future: refused; good: accepted;
  replayed: `409 replayed`; replayed after the window: refused as too old.
- `TestHandler_Devices` and `TestHandler_AccountReplace` now revoke with a
  signed body.

## 8. No way to refuse a call that is not encrypted

**Verdict: confirmed, as a design gap.** With `calls_encrypt = on` a call
that did not agree on keys always went plain - with a note in strong words for
a contact under `/e2e on` or verified, but never blocked. "Encryption is on
for this contact" so meant one thing for messages (never sent in clear) and
another for calls.

**Fix.** "Encryption is on for this contact" now means the same for calls as
for text:

- `calls_encrypt = on`: a call with a contact under `/e2e on` or verified
  (`PeerInfo::strict`) that did not agree on keys is not let through. Other
  contacts keep the never-blocked behaviour: plain, with a note.
- `calls_encrypt = required` (`Policy::calls_required`, also
  `ICQE2E_CALLS_ENCRYPT=required`) makes every contact strict.
- `calls_encrypt = off`: unchanged, no call encryption and nothing blocked.

A call that is not let through has its RTP and RTCP, bare or in TURN framing,
dropped both ways (`CallTable::blocks_plain` / `unagreed`: while such a call
is set up or went without keys - the client makes one call at a time - the
media hooks take every datagram socket of the call modules through the
encrypted path, which drops media no agreed call covers); STUN and TURN
control still pass, so a call that does agree can set up. When the call ends
(BYE, CANCEL, an error answer) nothing is held back any more. The chat says
`This call with ... is not let through: it is not end-to-end encrypted (...)`,
naming the reason: `/e2e on`, verified, or `required` in the ini. The patch
still writes `on`/`off`; the calls row counts a hand-set `required` as on and
keeps it rather than turning it back into `on` (`E2eIni.CallsRequired`); its
text is unchanged.

**Tests:**

- `callneg::tests::with_calls_on_a_strict_contact_is_blocked_and_a_plain_one_is_not`
  - `on` + `/e2e on` contact: blocked; `on` + verified: blocked; `on` +
  plain contact: plain with a note; after BYE nothing is held back.
- `callneg::tests::a_callee_without_the_add_on_or_with_calls_off_gets_a_plain_call`
  - updated: a verified contact's unencrypted call is not let through, on
  both sides.
- `crypto::tests::a_contact_under_e2e_on_whose_call_is_not_encrypted_is_not_let_through`
  - replaces `a_verified_contact_s_plain_call_is_said_in_strong_words_not_blocked`,
  through the engine.
- `callneg::tests::with_calls_required_a_call_that_did_not_agree_is_not_let_through`
  - `required`: blocked for every contact.
- `callneg::tests::with_calls_required_an_agreed_call_is_encrypted`
- `hook::calls_io::tests::with_calls_required_no_media_passes_plain` (real
  loopback sockets through the hooks)
- `config::tests::calls_encrypt_required_is_on_and_strict`

## 1. The auditor cannot tell an owner's action from the server's

**Verdict: confirmed.** The `revoke` leaf held only the device id
(`state/e2e_kt.go`, `e2eKTRevokeLeaf`), and the `delete` leaf nothing at all.
The auditor (`server/e2e/audit.go`, `apply`, the `revoke` and `delete` cases,
old lines 209-222) took any revoke of an active device and any delete of an
account with a key. The handler checked the owner's signature on
`DELETE /devices/{id}` (first part, finding 7) but did not hand it to the
store, so the log could not show it. A server could therefore revoke every
device of an account, or delete it, and then `reset` it or `publish` a key of
its own; every rule held and the auditor cosigned. Clients replayed the log
without any rules at all.

**Fix.**

- **Who said so goes into the log.** A `revoke` or `delete` now comes right
  after a leaf that names its authority, in the same transaction
  (`E2EAuthority`, `e2eKTAuthorityLeaf`):
  - `owner-revoke` (device id, `issued_at`, the account key's signature over
    the `revoke` message) and `owner-delete` (`issued_at`, signature over the
    new `delete` message) for the owner;
  - `recovery-revoke` (device id, why) and `recovery-delete` (why) for the
    operator, who has no account key: the management API's revoke, and
    `DeleteUser` (management API, ICQ legacy self-delete).
  `E2ERevokeDevice` takes the authority (an owner's request also needs its
  account key to still be the account's, inside the transaction, so a
  rotation in between cannot slip past). The bare `revoke` remains only for a
  rotation's devices that the new key did not re-sign.
- **A signed delete for the owner:** `DELETE /e2e/v1/account` with
  `{issued_at, signature}` over `"delete" | screen name | issued_at`, the same
  checks as a revoke (announced key, five minutes, once), store
  `E2EDeleteAccountKeys`. The add-on does not call it yet.
- **The auditor** (`AuditState.apply`) checks an `owner-*` signature against
  the account key current at that point, requires the announced `revoke` or
  `delete` to be the very next leaf (`AuditState.Pending`, kept in its state
  file), and refuses a bare `revoke` of a device that is not stale after a
  rotation (`auditDevice.Stale`) and any bare `delete`. Recoveries -
  `recovery-revoke`, `recovery-delete`, a `reset`, and a `publish` after a
  `recovery-delete` (`AuditState.Deleted`) - keep the rules and are
  cosigned, so the auditor does not stop on a legitimate recovery; each is
  logged once at WARN (`Auditor.Logger`, wired in `cmd/e2e-kt-auditor`).
- **The client** replays the log with the same rules (`kt::Replay::apply`;
  a broken rule is `SyncError::Violation`, a broken log as for a rewrite) and
  keeps, per account, the keys its key descends from by rotations
  (`LogAccount::chain`) and why a key came without the previous key's word
  (`LogAccount::new_identity`). `OwnKeys::pin` then treats a key so replaced
  as a new identity: the note "WARNING: the server replaced X's keys without
  X's key (operator recovery: ...)" every time it happens; for a contact
  verified or under `/e2e on` the key is held (`PinnedKey::held`) until
  `/e2e verify` or `/e2e accept`; others go on to the new key.
  `/e2e status` says it (`OwnKeys::key_recovery`). A rotation by the owner
  stays an ordinary change of safety number.
- **Encoding and rollout.** The authority is a leaf of its own, not new
  fields of `revoke`/`delete`: an add-on built before it parses a known kind
  with other fields as no leaf (`parse_leaf` returns `None`) and so as a
  rewritten log, but takes an unknown kind as a leaf that changes nothing.
  Old DLLs therefore read the new log exactly as before (they apply the
  `revoke`/`delete` and skip the authority leaf); no client has to be updated
  first. Auditors built before it refuse an unknown kind, and the new
  auditors refuse a bare revoke/delete from the old server, so the server and
  the auditors must be updated together, with no revoke or account deletion
  in between. The existing log (publishes and devices only) is valid under
  both.

**Tests:**

## 2. A network error on a trusted log becomes "no log"

**Verdict: confirmed.** `Engine::sync_log` set `OwnKeys::log_trusted = false`
before syncing (`crypto.rs`, old line 1001) and a `SyncError::Net` only set
`LogStatus::Failed`. `Engine::log_trust` mapped everything but `Ok` and a
sticky break to `Trust::NeverHadLog` (old line 1053), and `log_check`
returned "no constraints" whenever the status was not `Ok` (old line 1167).
`decrypt_olm` checked the log for a new inbound session only while
`log_trusted` (`keys.rs`, old line 1055). A server that made the log
unreadable for a client that had trusted it got trust on first use for new
contacts, changed keys, new devices and new sessions.

**Fix.** A fourth state, `kt::Trust::TemporarilyUnavailableAfterTrust`
(`Engine::trust_at`): a log that cannot be read (or has not been read yet
this sign-on) on a state whose copy was trusted before
(`LogState::was_trusted`: the log key pinned or entries kept - written only
after a sync that added up, so it is in the state file). The last trusted
copy stands, through the same frozen check as a broken log
(`Engine::frozen_log_check`, generalised with a reason): known account keys,
devices and sessions go on; a contact never pinned, a changed key, a device
without a session that the copy does not show are held with a note
(`Held::NotYet`, "the server's key log cannot be read right now"). Inbound,
`OwnKeys::log_trusted` is replaced by `OwnKeys::inbound_gate`
(`InboundGate::{Open, Log, Vouched, Frozen}`), set by the engine after every
look at the log; while it is unset, a copy that was trusted counts as
`Frozen`. Not sticky: the next sync that works lifts it. A state that never
trusted a log is still `NeverHadLog`. Every device of a contact left out by
the log now holds the message rather than sending it in clear.

**Tests** (`crypto.rs`):

- `a_trusted_log_that_cannot_be_read_takes_nothing_new_until_it_can` - log
  endpoints unreachable, directory up: a known contact still encrypts; a
  contact never checked is held and not pinned; its new session is unreadable
  and none is made; a changed key of a known contact is held; `/e2e status`
  says so; once the log is back the new contact encrypts.
- `a_log_never_trusted_that_cannot_be_read_is_no_log` (guard).

## 3. The auditor's freshness is only advice

**Verdict: confirmed.** `sync_log` set `LogStatus::Ok` and `log_trusted`
(`crypto.rs`, old lines 1016-1017) before `audit_log` (old line 1024), and a
stale audit was only a note. A server could keep newer cosignatures from one
client and feed it a fork: new contacts, devices and sessions were taken from
the fork while the auditor never saw it.

**Fix (the strict variant).** Once a pinned auditor has cosigned a checkpoint
that agrees with this copy (`LogState::audit_required`, from the persisted
`audits`/`audited`), new trust material is taken only from the part of the
log an auditor cosigned:

- the copy keeps a second replay, `LogState::vouched` up to `vouched_size`,
  the largest agreeing cosigned size (`LogState::audited_size`).
  `kt::vouch` brings it up after every look at the auditors, reading those
  leaves again and checking each against the leaf hashes the copy keeps (an
  old state file fills it at the next look);
- with a fresh cosignature (`LogState::audit_fresh`, within
  `kt::AUDIT_MAX_AGE`): a contact never pinned or a changed key must be the
  vouched part's (`Engine::vouched_log_check`), a device without a session
  must be in it (left out otherwise, with a note), and a new inbound session
  needs it (`InboundGate::Vouched`, `OwnKeys::vouched_shows`);
- without one (`kt::Trust::Unaudited`): known contacts, devices and sessions
  go on, anything new is held with a note until an auditor vouches again
  (`InboundGate::Frozen`).

A server that withholds cosignatures gains nothing: what it adds after the
auditor's last look is never in the vouched part. Trade-off: a key published
a moment ago is used a minute or two later, once the auditor has looked; a
first message from such a device may be unreadable until then (the sender's
client keeps sending pre-key messages until it hears back, and those open).

**Tests** (`crypto.rs`):

- `new_keys_are_taken_only_from_what_a_fresh_cosignature_covers` - an
  auditor cosigned 4 entries; the server adds a contact and a device of a
  known contact and keeps newer cosignatures back: the new contact is held
  and its new session unreadable, the device is left out ("not yet vouched
  for") while the known device still encrypts; an hour later, with no newer
  cosignature, the known contact still encrypts, the new one is held; once
  the auditor cosigns the log as it is, the new contact encrypts.
- `an_audited_log_says_so` and `an_old_or_missing_cosignature_is_a_warning`
  - updated: a contact published after the auditor's look is used only once
  it has looked; with a stale cosignature a contact never checked is held.
- `a_state_file_from_before_the_vouched_copy_fills_it` (guard).

## 4. File transfers go plain for a strict contact

**Verdict: confirmed.** With `files_encrypt = on`, a transfer that did not
agree on keys always went plain, also for a contact under `/e2e on` or
verified - only the wording got stronger ("file transfers are never
blocked"). Three paths led there: `filestream.rs` `FilePipe::tick` (old lines
866-876) after `HELLO_WAIT_MS` (4 s) without a key hello called `go_plain`
(old 794-800), which sent the held bytes (the OFT2 prompt) to the wire;
`hello_in` (old 676-683) did the same when the peer's first bytes were no
hello; `filesneg.rs` `go_plain` (old 904-915) made the transfer
`TState::Plain` after a decline, a missing offer or a failed send. The test
`filesneg::tests::a_peer_that_never_answers_gets_an_untouched_transfer`
asserted it for a strict contact. Besides, the offerer's accepted socket is
tied to a transfer only by its local port (`find_local`), and a pipe's
`Event::Plain` set the whole transfer plain: an outsider who connected to the
listening port first could turn the transfer plain.

**Fix.** Files follow the rule calls got in the first part (finding 8):

- `files_encrypt = off | on | required` (`Policy::files_required`, also
  `ICQE2E_FILES_ENCRYPT=required`); `required` makes every contact strict
  (`FileTable::set_required`, `Engine::set_files_required`, from `hook.rs`).
- A transfer with a strict contact (`PeerInfo::strict`: `/e2e on` or
  verified) or under `required` never goes plain. No offer or answer, a
  decline, a refusal or no keys: `TState::Blocked`, and every socket of it
  gets a pipe closed from the start (`FilePipe::refused`): shut both ways,
  `send`/`recv` answer `WSAECONNRESET`, no byte passes. No hello within 4 s,
  first bytes that are no hello, or the end of the stream while waiting: the
  pipe asks `KeySource::must_encrypt`, and `FilePipe::block` drops the held
  bytes and closes the connection (`Event::Blocked`). The chat says, once per
  transfer, that the file "was not sent" and why (`policy::file_blocked_note`:
  `required` in the ini, verified, or `/e2e on`).
- A connection that is not authenticated decides nothing: a block at
  connection level closes only that connection; the transfer stays offered,
  so an outsider who connects first cannot make it plain and the real peer
  can still connect with its MAC'd hello. An agreed transfer still fails
  closed on junk and stays keyed.
- Other contacts keep today's compatibility: plain, untouched, with a note.
- Patch: the files row still writes `on`/`off`; a hand-set `required` counts
  as on and is kept (`E2eIni.FilesRequired`, as `CallsRequired`).

## 5. Direct IM goes past the container

**Verdict: confirmed, conditional on the clients using it.** The add-on
encrypts only what goes over the BOS connection: ICBM channel 1 and the
channel-2 server relay. `icbm::decode_channel` passes every channel-2
rendezvous of the `0946134x` family untouched by design, and that includes
AIM Direct IM - a rendezvous with `CapDirectICBM`
(`09461345-4C7F-11D1-8222-444553540000`, `wire.CapDirectICBM`), after which
text travels as ODC frames on a peer TCP connection. `CapDirectICBM` stayed
in the capability list the client announces in `LocateSetInfo`. A second
path is the ICQ direct-connection protocol: each client publishes its
address and port in the DC info (TLV `0x000C` of `OServiceSetUserInfoFields`
`0x0001/0x001E`), which the server hands to contacts in "buddy arrived".
Neither path was touched, so a client that used one would send text in
clear, even to a contact under `/e2e on` or verified. Whether ICQ 6.5/7.2 use
either is not visible in the code; it needs the live test below.

**Fix** (`core/src/direct.rs`, encrypt mode only; observe, harness and
`e2e = off` are unchanged):

- `CapDirectICBM` is taken out of TLV `0x0005` of the outbound
  `LocateSetInfo`, with and without a session.
- Every direct-IM proposal and acceptance is dropped in both directions;
  cancels pass. For a proposal the client made, the client is handed a
  cancel from the contact (`direct::cancel_to_client`, via `Answers::owe`)
  and the `ICBMHostAck` it asked for, so it does not wait. With
  `ICQE2E_NO_INJECT` the frame is turned into a cancel in place
  (`direct::as_cancel`).
- The first 9 bytes of the DC info (address, port, connection type) are
  zeroed without changing its length, in the client's own
  `SetUserInfoFields` (`strip_own_dc`) and in every contact's user info in
  "buddy arrived" (`strip_contacts_dc`): neither side has an address to open
  an ICQ direct connection to. Zeros are what the server sends when the TLV
  was never set.
- File transfer (`CapFileTransfer`) and calls (channel 6) are not touched.

**Tests** (each failed with the fix reverted):

- `stream::tests::an_outbound_direct_im_proposal_never_reaches_the_wire_and_the_client_gets_a_cancel`
- `stream::tests::an_inbound_direct_im_proposal_is_not_handed_to_the_client`
- `stream::tests::with_injection_off_a_direct_im_proposal_goes_on_only_as_a_cancel`
- `stream::tests::the_direct_im_capability_is_not_announced_while_encrypting_and_is_otherwise`

- guard: `stream::tests::file_transfer_and_call_frames_pass_untouched_while_direct_im_is_refused`;
  unit tests in `direct::tests`.

**Limits.** An inbound proposal is dropped silently (the contact's client
times out). `CapDirectICBM` in contacts' capability lists is left alone
(removing it would change lengths); their proposals are dropped anyway. DC
info in other SNACs (a Locate user info reply) is not zeroed.

**Live test** (also in `tools/icq-e2e/README.md`, "Direct IM and direct
connections are kept off"): two machines on one LAN with the add-on and
`files_log = on`. Baseline with `ICQE2E_MODE=observe`: chat, send a file,
and use "Direct IM / direct connection" if the client offers it; look in the

`OUT capabilities: direct IM left out while encrypting` at sign-on,

## 6. The ids of inbound sessions grow without bound

**Verdict: confirmed.** `OwnKeys::remember_inbound` (`keys.rs`, old line 715)
kept every inbound session id for `INBOUND_ID_KEEP` (29 days) with no limit
per device; a contact - or anyone with a device in the log - could make the
state file grow by sending pre-key messages with fresh sessions, each also
spending one of our one-time keys.

**Fix** (`OwnKeys::inbound_allowed`, checked in `decrypt_olm` after the
replay check and before the directory lookup, so a refused message spends
nothing):

- **rate:** at most `INBOUND_SESSIONS_PER_WINDOW` = 10 new sessions per
  (contact, device) within `INBOUND_RATE_WINDOW` = one hour; the next is
  unreadable with a note naming the anomaly, and sessions are taken again
  after the hour. A real client starts a new session when it loses its state
  or links a device, a few times a year;
- **cap:** at most `INBOUND_IDS_PER_DEVICE` = 200 ids kept per device. When a
  device has that many younger than `INBOUND_ID_KEEP`, it gets no new
  session until the oldest expires, with a note. No id is dropped to make
  room: a dropped id would let its pre-key message make the session again,
  which is the replay of the first part's finding 3. At 10 an hour the cap is
  reached after 20 hours of abuse, and the device is then refused for at most
  the 29 days the ids are kept - a denial of service to that one device of
  that one contact, which is what its abuse earns, never a replay.

The number of (contact, device) pairs is bounded by the accounts and devices
the directory and the log hold; the state file grows by at most 200 ids per
such pair.

**Tests** (`keys.rs`):

- `new_inbound_sessions_from_one_device_are_limited_per_hour` - ten new
  sessions open, the eleventh is refused with the note and spends no
  one-time key, and opens after the hour.
- `a_device_with_too_many_kept_session_ids_waits_and_none_is_dropped` - with
  200 ids kept, a new session is refused, the oldest id is still remembered
  and none was dropped; once the oldest has expired, a new session opens.

## 1. An auditor's word is required only after its first cosignature

**Verdict: confirmed.** `LogState::audit_required` (`kt.rs`, old line 679)
was `audited.is_some() || !audits.is_empty()`: true only once a cosignature
had been received. With auditors pinned by the patch (`auditors =`,
`ICQE2E_AUDITORS`) or pinned on first sight in `LogState::auditors`, but
`GET /log/cosigned` empty - a server that simply withholds every
cosignature - `Engine::trust_at` (`crypto.rs`, old lines 1084-1102) said
`Trusted`, `set_inbound_gate` chose `InboundGate::Log` rather than
`Vouched`, and `log_check` took new contacts, devices and sessions from the
log alone. The test `an_old_or_missing_cosignature_is_a_warning` asserted
exactly that ("No auditor ever did: messages go"). A state that had never
read a log was also trust on first use whenever the log could not be read,
auditors configured or not.

**Fix.**

- `LogState::audit_required` is also true when an auditor is pinned in the
  copy (`!auditors.is_empty()`). `OwnKeys::audit_configured` (not in the
  state file) is set by `Engine::set_auditors` when the ini names auditors,
  so the line counts before anything is pinned. `OwnKeys::audit_required`
  combines the two, and every decision uses it (`trust_at`,
  `set_inbound_gate`, `log_check`, `frozen_log_check`,
  `OwnKeys::log_allows_inbound`).
- No fresh cosignature yet: `kt::Trust::Unaudited`, never `Trusted`. Known
  contacts, pinned keys and sessions go on (`frozen_log_check`); a contact
  never pinned, a changed key, a device without a session and a new inbound
  session wait until an auditor vouches.
- The inbound gate is `Vouched`, never plain `Log`, while an auditor is
  required; `log_allows_inbound` also turns a `Log` gate into `Vouched` and
  an unset (`Open`) one into `Frozen` then.
- With an auditor configured, a log that cannot be read, has not been read
  yet, or that the server says it does not keep is
  `TemporarilyUnavailableAfterTrust` even on a state that never trusted a
  log - not trust on first use; `/e2e status` says so.
- Only with no auditor configured or pinned anywhere does the old behaviour
  stay (no auditor: the log alone; no log on an older server: trust on
  first use).
- `kt::audit` with an `auditors =` line also drops `LogState::audited` when
  it is the word of an auditor no longer trusted, as it already did for
  `audits`.

## 2. A stale cosignature moves the vouched part as far as it covers

**Verdict: confirmed.** `audit_fresh` asked whether *any* agreeing
cosignature was fresh, while `audited_size` took the largest size over
*all* of them, stale ones included; `Engine::audit_log` (`crypto.rs`, old
lines 1110-1131) brought `vouched_size` up to `audited_size`. With auditor A
stale over 100 entries and auditor B fresh over 50, the copy counted as
audited and was vouched up to 100: a key in entries 51-100 that no auditor
had looked at within the hour was taken.

**Fix.** `audited_size` is gone. `LogState::fresh_audited_size(now)` is the
largest size of the agreeing cosignatures with `time + AUDIT_MAX_AGE >= now`
(no more than the copy), taken from the same set `audit_fresh` uses
(`LogState::fresh_audits`); `audit_log` moves `vouched_size` only by it,
with the `now` of the look that just read the cosignatures. The vouched part
never shrinks: what a fresh cosignature once covered stays vouched for.

## 3. An owner's signed action is checked for its signature, not its age or reuse

**Verdict: confirmed.** The auditor (`server/e2e/audit.go`, the
`owner-revoke` and `owner-delete` cases) and the client's replay
(`kt::Replay::apply`) checked only that the account key signed the revoke
or delete message. The handler takes such a request only within five
minutes of its clock and only once (`server/e2e/handler.go`,
`revokeWindow`, `usedSignatures`), but nothing held the log to that: a
server that kept an owner's signature could log it later - most usefully an
`owner-delete` once the owner publishes the same account key again, which
would delete the account again "by the owner", with no recovery warning.
Today the add-on never calls `DELETE /account`, so only a revoke signature
could be kept, and a device is never revoked twice; hence medium, high once
the add-on deletes.

**Fix.**

- One constant, `OwnerSignatureWindow` (5 min, `server/e2e/sign.go`). The
  handler's `revokeWindow` is now that constant; the client has
  `kt::OWNER_SIGNATURE_WINDOW` = 300 s, held to the same value by the
  shared vectors.
- The auditor (`AuditState.ownerAction`) and the replay
  (`kt::owner_action`) refuse an `owner-revoke` or `owner-delete` whose
  `issued_at` is more than the window from its own leaf's time, either way.
  The server stamps the leaf with the same clock it checked the request
  against, so a real one is always within it.
- A given owner's action - kind, account, device (0 for a delete) and
  `issued_at`, that is the signed message - may appear in the log only once
  (`AuditState.OwnerUsed`, `Replay::owner_used` and `LogState::owner_used`,
  kept in their state files; optional, so old state files read).
- `sharedKTVectors` gained four leaves and five sequences (a revoke issued
  301 s before its entry, one exactly 300 s before, a delete 301 s after,
  a delete's signature logged a second time after the same key is published
  again, and a second delete with a new signature): Go and Rust come to the
  same verdicts.
- The in-memory directory of the Rust tests stamps an owner's revoke with
  its `issued_at`, as the server does.

**The existing log stays valid.** The new rules touch only `owner-revoke`
and `owner-delete` leaves. The production log holds only `publish` and
`device` leaves today (not checked from here: the production machine was
not touched), so new auditors and add-ons replay it exactly as before.

# Fourth review: bootstrap and interception

Two independent reviews of commit `31a42a5` looked at how the add-on gets
into the client and what happens when that, or anything under it, fails:
the loaders, the hook installation, the socket hooks, the stream rewriter
and the patches that put the add-on in. Their nine points (A-I) were all
confirmed in the code. The crypto, Olm and key-log logic was not changed,
except where its callers now ask the protection gate.

The common thread: every module decided its own fallback, and most
fallbacks were "let it through as it is". The fix is one gate
(`core/src/gate.rs`) that every send, receive and connect path asks, per
traffic class, and that never answers "as it is" for protected traffic
because of an internal failure.

Line numbers are those of `31a42a5`. As in the earlier parts, the tests
that guard a fix were run against the old logic (the fix put back
temporarily) and failed there; the ones listed under "checked against the
old logic" below were run so, the others test code that did not exist
before.

## A. Encrypt mode without a session passes plaintext

**Verdict: confirmed.** `ensure_session` (`hook.rs` 503) returned without a
word when there was no key directory (507), no UIN yet (510) or the state
file could not be opened (`account_session` logged "encryption off" and gave
`None`, 426). `harness_send` and `harness_recv` then called
`push_sessionless` (1089, 1366), which for every mode but `e2e=off` ran the
plain rewriter `rw.push` (182): a message to a contact under `/e2e on` or
verified left as typed, and a container from a contact reached the client as
armoured text. Only a state file locked by another process was already fail
closed (`locked_out`, first audit finding 6), and stays so. The first
audit's "Limit" under finding 6 ("a state file that cannot be read still
turns encryption off") is what this removes.

**Fix.** The crypto state is explicit (`gate::CryptoState`):
`WaitingForIdentity`, `Ready(session)`, `Unavailable(reason)`,
`LockedOut(session)`. `ensure_session` returns it, with a reason for every
way of having no session; a state file that cannot be opened is said once
and tried again after a minute (`RETRY_STATE_AFTER`), not on every frame.
Without a session, encrypt mode runs the stream through `gate::Withheld`,
an engine that holds every message with a note ("The message to X was NOT
sent: <why>. Nothing is sent unencrypted because of it"), shows no
container ("could not be read: <why>"), answers a `/e2e` command and
announces no key. With `ICQE2E_NO_INJECT` the held frame goes on with its
text withheld, as for any held message. Control frames (sign-on, MOTD, user
info) pass, so the token and the account are still learned and the session
opens as soon as it can. The plain rewriter is used only in harness and
observe mode; `e2e=off` keeps its own engine. The notes reach the chat
through the same delivery as the session's (`deliver_notes`), together with
notes the gate itself has queued.

## B. A FLAP stream that loses its framing turns raw for good

**Verdict: confirmed.** In `StreamRewriter::feed` (`stream.rs` 366) any
header that was not FLAP set `State::Raw` and released the rest, also on a
stream already recognised as FLAP; from then on every byte both ways passed
the rewriter untouched. The test `desync_later_releases_held_bytes` (1124)
asserted exactly that.

**Fix.** A stream still opening may turn raw (another protocol: a peer
connection, a proxy). A stream recognised as FLAP that meets a bad header
turns `State::Broken`: the bytes from the bad header on are dropped,
nothing passes afterwards, `finish` releases nothing, and the hooks reset
the connection (`reset_broken_stream`: `WSAECONNRESET`, the socket refused
for good, a note "its data stopped making sense to the add-on"). The frames
the same call had rewritten before the bad header are dropped too; the
client reconnects. `desync_later_releases_held_bytes` is replaced by
`a_flap_stream_that_loses_its_framing_is_broken_not_raw`.

## C. IAT patching is not atomic

**Verdict: confirmed.** `patch_iat` (`hook.rs` 1971) wrote the slots one by
one as it walked the imports: an error found later ("imports not bound
yet") returned `Err` after earlier slots had already been changed, with no
rollback; `write_thunk` (2089) returned `false` when `VirtualProtect` failed
(2096) and `patch_iat` could still return `Ok` without that slot. Every read
was a raw `read_unaligned` at `base + offset` (1938, 1979) with no bound.
`install_into` set `INSTALLED` (1727) once `send` and `recv` were in,
whether or not `connect` was - with `tls=on` a missing `connect` hook means
no mapping to the TLS port.

**Fix.**

- `core/src/pe.rs`: a bounds-checked PE reader over one slice `[base, base +
  SizeOfImage)`, checked arithmetic on every RVA, limits on table lengths
  (descriptors, thunks, names), PE32 only for the 32-bit thunks. The hooks
  build the slice from the module's `SizeOfImage` (`loaded_image`); the
  export table lookup goes through it too.
- Two phases (`hook.rs`): DISCOVER (`discover`) reads every import slot of
  the Winsock DLLs that one of the hooks is for, checks each is bound and
  changes nothing; COMMIT (`commit`) keeps the originals first, then writes
  every slot through a `ThunkWriter` (the real one: `VirtualProtect`, one
  aligned atomic store, protection restored). If a write fails, every slot
  written before it is put back and the install counts as failed. The
  result is the set of hooks that went in (`gate::HookMask`).
- Whether that set is enough is the gate's call: `HookMask::required_for`
  needs `send`/`recv` in every mode but observe, `connect` with TLS (also
  `tls=off`, for the guard ports) and in encrypt mode, `accept` with file
  encryption. A required hook that is missing makes the bootstrap `Fatal`
  (`Gate::settle`). The hooks that could go in are committed even then -
  all of them or none - so that they can refuse what they see; leaving the
  module unpatched would let it all through.
- The call modules (`hook_calls.rs`) use the same two phases.

The real clients import every hooked function: `coolcore59.dll` (7.2) and
`coolcore49.dll` (6.5) import `send`, `recv`, `connect`, `closesocket`,
`WSAAsyncSelect`, `ioctlsocket`, `getpeername` and `accept` from
`wsock32` (checked on the files of both clients; they also import `sendto`
and `recvfrom`, which no hook needs for messages).

## D. Hooks that fail to install are reported nowhere

**Verdict: confirmed.** `start` (`hook.rs` 1531) reported nothing when no
way in found the module; the polling thread logged "gave up after 60s"
(1785) and the add-on then did nothing, while the client - whose module
was never patched - connected as it pleased. The user was not told.

**Fix.** The bootstrap (`gate::Bootstrap`) is `Starting` until the policy is
read and the install has an outcome, then `Ready(mask)` or `Fatal(reason)`.
In any protecting policy (`gate::protecting`: encrypt and harness mode, and
`e2e=off` with TLS) `Fatal` means every `connect` (`WSAECONNREFUSED`),
`send` and `recv` (`WSAECONNRESET`) the hooks see is refused
(`admitted`), the log says why once per socket, and a message box says so
once: "the add-on cannot protect this ICQ (<why>). The client is not
allowed to connect without the protection it was set up with." The module
never appearing within 60 s is `Fatal` too. Where the hooks are not in
place at all, nothing can be refused from inside: that case is G's.

## E. Call and file media without their hooks

**Verdict: confirmed.** `hook_calls::on_load` only logged "could not patch"
(896) and, after its retries, "gave up patching" (920); the call then went
on with its media on sockets the add-on never saw. With
`calls_encrypt=required`, or a contact under `/e2e on` or verified, the
promise "not let through unless encrypted" rested on media hooks that were
not there. The same held without a session (finding A): the stand-in engine
of the old code never saw the call or the transfer, so no key exchange and
no block happened. A file transfer's data goes over the networking module's
own `accept`/`connect`/`send`/`recv`, which C now makes required with file
encryption.

**Fix.** The gate decides the `Media` and `File` classes on the BOS
connection, before the engine's key exchange (`stream.rs`, `emit`):

- `gate::media`: with `calls_encrypt` on, a call whose contact's policy
  cannot be told (no session, or a locked-out one: `Crypto::strictness`
  answers `None`) is blocked; with the call hooks failed
  (`gate::MediaHooks::Failed`, set by `hook_calls` when patching fails for
  good) a call that must be encrypted (`required`, `/e2e on`, verified) is
  blocked, and any other goes as it is with a note ("the add-on could not
  take over the call's media, so the call is not end-to-end encrypted") and
  without a key exchange that would claim otherwise. Blocked means the
  call's SIP frames are dropped both ways, so the call is never set up; the
  chat says "This call with X was not let through: <why>" once a minute.
- `gate::file`: with `files_encrypt` on, a proposal or an acceptance whose
  contact's policy cannot be told is dropped both ways with a note; a cancel
  always passes. Missing peer-socket hooks make the bootstrap `Fatal` (C).
- `Crypto::strictness` is new on the engine trait (callers asking the gate):
  the engine answers from its settings (`peer_info`), `None` while locked
  out; the stand-in engine answers `None`.
- The call modules load when a call starts; a module that loads before the
  policy is read is patched from a thread once it is (`calls_io::later`).
  A patch that fails for good says once in the chat which calls are now
  refused.

## F. `-uin` is read from UTF-16 as a C string

**Verdict: confirmed.** `uin_from_command_line` (`hook.rs` 461) read the
`GetCommandLineW` string through `CStr::from_ptr`: the second byte of the
first UTF-16 unit is zero, so the "command line" was one character long and
`-uin` was never found. The account was learned from the sign-on instead,
which is why nobody noticed.

**Fix.** The command line is read as UTF-16 up to its NUL (at most 32767
units), turned into a `String` lossily and split by the rules of
`CommandLineToArgvW` (`split_command_line`: quotes, `2n`/`2n+1`
backslashes before a quote), then `-uin`/`/uin` and a decimal UIN are taken
(`uin_from_args`). No new DLL dependency (shell32).

## G. The external fuse exists only for the TLS row

**Verdict: confirmed.** The guard ports - the sign-in pointed at ports that
do not work in plaintext, so a client without the add-on cannot sign in -
were written only with the TLS row (`Icq65Client.cs` 1895,
`Icq72Client.cs` 371). With the messages row alone the sign-in stayed on
5190 / 8082: rename the DLL and the client signed in and sent every message
in clear, without a word. With `tls=off` the add-on mapped nothing
(`hook_tls.rs` 369), so the guard could not have worked there either.

**Fix.**

- Patches: the guard ports are written whenever a protecting row is
  applied - TLS, or the messages row on its own - with the sign-in row (6.5
  `MCore.dll` `ServerPort` 5194; 7.2 `AppConfig.xml` both sign-in ports 5195
  and `skipSources`). 6.5 decides after the DLL and the ini are in place
  (`GuardWanted`: our DLL in place, the ini ours, `e2e` or `tls` on); 7.2
  edits `AppConfig.xml` when either row is wanted. The row item is renamed
  "sign-in only through the add-on"; it counts in no row while it agrees
  with the ini and shows the TLS row unapplied when it does not. The summary
  says which ports and that only the add-on reaches them.
- Add-on: with `tls=off` the guard ports of the server go to its plain ports
  on the same host - 5194 to 5190, 5195 to 8082 (`route::GUARD_PORTS`,
  `Route::guard`, `hook_tls::plan_guard`, `ConnectPlan::Remap`);
  `getpeername` reports the guard port the client asked for. A guard port
  with a name that does not resolve is refused. With TLS the mapping is the
  one it was (to the TLS port).
- The decision: the guard ports are reachable only through the add-on. With
  `tls=off` the add-on maps them to plain 5190 / 8082 - TLS-off users still
  sign in, through the add-on - and a client without it gets the TLS-only
  5194 or the silent 5195 and does not sign in. The server, seeing the
  client on its plain listener, hands out its plain BOS host, which passes
  as before.

So whenever any protecting row is ticked, a client without a working add-on
cannot sign in: missing, renamed, not loaded, or failing before its hooks
are in place.

## H. Loader work in `DllMain`

**Verdict: confirmed.** `loader-msimg32` called `LoadLibraryW` on
`system32\msimg32.dll` inside `DllMain` (`resolve_real`, 40/62), which
`DllMain` must not do under the loader lock. Both loaders then called
`install`, which in `DllMain` read `icq-e2e.ini` and wrote the log
(`Policy::from_env`, `lib.rs` 74), and through `start` patched, took
mutexes, registered the loader notification and created threads.

**Fix.**

- `loader-msimg32`: no library is loaded in `DllMain`. Each forwarding
  thunk jumps through a pointer that starts at a resolving stub of ours
  (`lazy_*`, naked: it calls `resolve_all` and jumps on, the caller's stack
  untouched). `resolve_all` resolves the five exports once (`Once`): the
  genuine module already loaded by its full path, else `LoadLibraryW` then.
  The add-on's bootstrap thread calls it first (`install_with(prewarm)`), so
  in practice the first GDI call finds the exports resolved. Should the
  genuine DLL be missing, each export answers `FALSE` with its arguments
  popped instead of the process failing to start.
- Core: under the loader lock only `start_from_loader` runs: the loader
  notification is registered (ntdll is always loaded), a networking module
  already mapped is patched, and the bootstrap thread is created. Patching
  is memory work only (the PE reader, `VirtualProtect`, slot stores); its
  log lines are kept in memory (`log::defer`) and written by the bootstrap
  thread. The bootstrap thread - which starts only once the loader lock is
  released - runs the loader's prewarm, reads the settings, writes the log,
  polls for the module as the fallback and settles the gate.
- Why no `connect` can slip out before the install: the synchronous
  guarantee stays - the notification still patches the networking module the
  moment it is mapped, before any of its code runs (it is the one piece of
  work kept under the loader lock, by design: there is no later moment that
  is still before the module's code). What the hooks may not know at that
  moment is the policy; so the gate starts `Starting`, and a hooked
  `connect`, `send` or `recv` made before the bootstrap has read the policy
  waits for it (up to 10 s) and is refused if it does not come. A hook called
  on a thread that holds the loader lock (none of the clients' sign-in paths
  does) waits out the 10 s, since the bootstrap thread cannot start until
  then, and is refused. `policy()` no longer pins observe mode when asked
  before the policy is read, and the TLS setup is not built or kept from a
  policy not read yet.

## I. The patch trusts the add-on DLL by its version resource

**Verdict: confirmed.** `IsOurE2e` (`Icq65Client.cs` 1103,
`Icq72Client.cs` 1330) took a DLL for the add-on when its `ProductName` and
`InternalName` said so - any file can say so - and the patch copied it into
the client as `msimg32.dll` or `tbdiag.dll`.

**Fix.** `tools/common/Build-Patches.ps1` builds the add-on first, hashes the
DLL each patch hands out and embeds the line `<SHA-256> <file name>` in that
patch exe as the resource `e2e-manifest.txt` (`-p:E2eManifest=`, an
`EmbeddedResource` in `Icq65Patch.csproj` / `Icq72Patch.csproj`).
`E2eManifest` (`patcher/Common`) reads it. A DLL next to the patch is put in
only when its hash is on the list (otherwise the rows show "not the E2E
add-on this patch was built with"); one already in the ICQ folder that is
not on the list does not count as ours, and Apply replaces it; after the
copy the hash is checked again. A patch built without the add-on
(`-NoPlayer`, no cargo) has no list and accepts no DLL. Authenticode can come
later; this needs no certificate.

## The design, in one place

`core/src/gate.rs`:

- `Bootstrap { Starting, Ready(HookMask), Fatal(reason) }`, with the
  install's outcome and the policy settled into it (`Gate::settle`);
  `Fatal` is sticky for the process.
- `CryptoState { WaitingForIdentity, Ready(Session), Unavailable(reason),
  LockedOut(Session) }`, per account.
- `MediaHooks` per call module.
- The classes and their pure decision functions: `admit` (`Control`),
  `message` (`Message`), `media` (`Media`), `file` (`File`), each returning
  `Pass`, `Protect` (to the engine, which encrypts or holds per contact),
  `Plain(note)` (a compatibility case, with a note), `Hold(note)` or
  `Block(reason)`.
- `Withheld`, the engine of an account without keys.

Who asks: `hook_send`, `hook_recv` (through `tls_gate`) and `hook_connect`
ask `admit` first; `harness_send`/`harness_recv` pick the engine by the
crypto state (`Protect` with a session, `Hold` through `Withheld` without);
the stream asks `media` and `file` before the engine's key exchange. No hook,
stream or install path decides a fallback of its own any more: a panic in a
hook body is still `fail_closed` (first audit, finding 1), now one of the
paths of `close_for_good`, and a panic while planning a `connect` refuses it
in a protecting policy instead of choosing "plain" by itself.

## 1. A plaintext ICBM from a protected contact is shown

**Verdict: confirmed.** `rewrite::process_crypto_snac` (`rewrite.rs`
535-537) returned the frame unchanged whenever the inbound text held no
armoured container: "a peer without the add-on sends plain text, which is
left exactly as it arrived". Nothing asked whose name it was in. The server -
or anyone it relays for, the management API's `POST /instant-message`
included - could therefore show any text in the name of a contact under
`/e2e on`, verified, or seen encrypting for years, and the user had no way
to tell it from the contact's own encrypted words. Channel 4 and offline
messages of other types than plain were not even looked at.

**Fix: the second central invariant.** If a contact is protected, the client
never shows a message in their name that did not pass end-to-end
authentication. One decision, `Crypto::plain_inbound` (new on the trait, no
default), asked by one function, `rewrite::plain_in`, for every inbound
SNAC that is not an armoured container and whose text the client shows as
the contact's words (`rewrite::shown_text`):

- channel 1 (fragment 1), channel 2 server relay (type-2), channel 4
  (old-style ICQ, now parsed: `icbm::ch4_text`), and ICQ offline replies;
  on channels 2 and 4 and offline, the message types `plain`, `URL` and
  `contacts` (`icbm::SHOWN_TYPES`). Plugin messages (tZers, Xtraz),
  away-message requests and authorization events carry no words of the
  contact's and pass. Chat rooms are not end-to-end encrypted and are not
  touched; away messages and profiles are not messages.
- `Engine` (`policy::plain_inbound_refusal`): `/e2e off` - shown;
  automatic, never seen encrypting and not verified - shown (a contact
  without the add-on, compatibility); `/e2e on`, seen encrypting, or
  verified (also a verified contact whose key changed and is held) - **not
  shown**. Locked out (another process holds the state file), the settings
  cannot be read - not shown.
- `gate::Withheld` (no session: `Unavailable`, `WaitingForIdentity`): the
  policy cannot be determined, so every contact counts as protected, as for
  calls and files at the gate - not shown.
- `Disabled` (`e2e=off`): nothing is protected on such an install - shown.
- Not shown means the frame is dropped (its ack request hidden, as for a
  container). With `ICQE2E_NO_INJECT` the frame stays with the add-on's
  words in place of the text, never the original. The chat gets
  `WARNING: a message that was not end-to-end encrypted arrived in <uin>'s
  name and was not shown (<why>) ...` (`policy::plain_dropped_note`), at most
  once a minute per contact (`crypto::plain_dropped`, every drop is logged),
  and a security alert (finding 2).
- `/e2e plain` is about sending and does not apply inbound.

**Trade-off.** A protected contact who really writes without encryption -
from a second client without the add-on, or with encryption off on their
side - is not shown; the warning says how to proceed (`/e2e off` in that
chat shows their unencrypted messages again, and sends ours unencrypted).
A tZer the server turns into plain text ("tZer: <name>") for a client that
plays no tZers is plaintext too and is not shown for a protected contact.

**tZers between 6.5 and 7.2 keep working.** ICQ 6.5 sends a tZer as a

## 2. `[ICQ E2E]` notes are forgeable

**Verdict: confirmed.** A note is put into the chat as an incoming message
from the contact (`stream::put_note`), marked only by its `[ICQ E2E]`
prefix (`stream::note_text`). Any message in the contact's name - in clear
from an automatic contact, or end-to-end encrypted by the contact
themselves - could start with the same prefix and read as the add-on
saying "Encryption is on", "100002 is marked verified" or a safety number.

**Fix.**

- (a) **The marker is the add-on's alone.** `policy::looks_like_note`
  recognises the marker at the start of a text in any case, with any
  whitespace or invisible characters in it (zero-width, soft hyphen,
  direction marks), wrapped in HTML, written with `&nbsp;` or numeric
  entities, in full-width forms or with Cyrillic/Greek look-alike letters
  (also as Latin-1 shows their CP1251 bytes). `policy::unmark` then puts
  `(from <uin>) ` in front of what shows first - after the leading tags and
  whitespace, in the text's own charset (8-bit or UCS-2), so the client
  still renders it. Applied to inbound plaintext that is shown
  (`rewrite::plain_in`, every path of finding 1, `e2e=off` included) and to
  every decrypted text (`Inbound::Text` in `process_crypto_snac`). The
  add-on's own notes are made after the rewriter and keep the marker.
- (b) **Security events outside the chat.** `alert.rs` (new) shows them in a
  Windows message box of the add-on's own, which nothing from the network
  can produce: the answers to `/e2e safety`, `/e2e verify`, `/e2e unverify`
  and `/e2e accept`; a pinned key change that holds messages (a verified
  contact's, or a protected contact's replaced by the operator); the key log
  broken (rewritten, split view, rule violation) or unaudited (no fresh
  cosignature); an unencrypted message in a protected contact's name that
  was not shown. Never blocking: each box comes from a thread of its own,
  never from a hook or the client's UI thread. Rate-limited: one event key
  at most once a minute, at most three boxes open (more are logged only).
  `security_popups = on|off` in `icq-e2e.ini` (`ICQE2E_SECURITY_POPUPS`),
  on unless it says off; the patch keeps a line added by hand. Only the
  add-on's bootstrap switches the boxes on, so the tests and the test host
  never open one (the unit tests collect them instead).

**Tests:**

- `policy::tests::the_note_marker_is_recognised_in_every_disguise`
- `policy::tests::a_marker_from_the_network_is_shown_as_the_contacts_in_every_charset`
- `stream::tests::text_from_the_network_cannot_pass_for_a_note` - in clear on
  every path of finding 1, and decrypted; the add-on's own note keeps the
  marker; ordinary text is untouched.
- `crypto::tests::a_verified_contacts_key_change_is_a_security_alert` - and
  `/e2e accept`'s answer; an unverified contact's change stays in the chat;
  `security_popups` off raises nothing.
- Alerts asserted in `session::tests::an_unencrypted_message_in_a_protected_contacts_name_is_never_shown`
  (every drop, `/e2e safety`, `/e2e verify`),
  `crypto::tests::a_log_broken_after_it_was_trusted_takes_nothing_new_until_resetlog`
  and `crypto::tests::an_old_or_missing_cosignature_is_a_warning`.
- `alert::tests::one_key_is_shown_once_a_minute_and_the_switch_holds_all`,
  `config::tests::security_popups_are_on_unless_switched_off`.

**Limit.** A note in the chat still looks like a message from the contact;
what makes it trustworthy is that only the add-on can start one with the
marker, and that the events that decide whom to trust are also in the box.

## 3. `finish` hands a partial frame to the client

**Verdict: confirmed.** `StreamRewriter::finish` (`stream.rs` 421-427)
released whatever was held at the end of the stream, in every state but
`Broken`: in a FLAP stream that is the start of a frame the rewriter never
processed - the header and the start of a message, a container or the
plaintext of one - handed to the client (the only caller is the inbound
`recv` at EOF, `hook.rs`). The test `finish_releases_a_partial_frame`
asserted exactly that, as did the end of
`hook::socket_tests::rewrite_over_a_real_socket`.

**Fix.** `finish` returns how many bytes it dropped and releases only in
`Raw` (where nothing is ever held: every byte passed at once). `Opening`:
the start of a stream not yet recognised is dropped - no FLAP frame can be
in it and nothing follows. `Flap`: the partial frame is dropped. `Broken`:
nothing, as before. The hook logs the bytes dropped and reports the end of
the stream.

**Tests:** `stream::tests::finish_hands_on_no_partial_frame` - replaces
`finish_releases_a_partial_frame`, which enshrined the unsafe behaviour:
opening, FLAP both ways on the harness and the crypto path, raw.
`hook::socket_tests::rewrite_over_a_real_socket` - its last step now
expects the partial frame to be dropped over a real socket and the end
reported.

## 4. "frame would exceed 64 KiB; sent unchanged"

**Verdict: confirmed fail-open, not reachable by normal ICQ 6.5/7.2 text.**
`StreamRewriter::emit` (`stream.rs` 688) put the original frame on the wire
when a rewritten payload would exceed a FLAP frame: on the crypto path the
plaintext of an outbound message, or an inbound container (or, since
finding 2, a plaintext that starts like a note). Reachability: an outbound
container is at most `rewrite::MAX_TEXT` (7000) bytes and the rest of a
client's ICBM is well under 1 KiB; the server relays no ICBM over 8000 bytes
(`foodgroup/icbm.go`, `maxICBMLen`); a decrypted text is shorter than its
container. Only a frame padded to within a few bytes of 64 KiB - which only
a malicious server can send, inbound - reached it, or a client building a
58 KiB ICBM itself.

**Fix.** On the crypto path (`push_crypto`) an oversize result drops the
frame (its ack request hidden) with a note - "The message to X was NOT
sent: encrypted, it would not fit in one frame. Nothing was sent
unencrypted", or "A message from X was not shown ...". With
`ICQE2E_NO_INJECT` a stand-in that does not fit drops the frame too, never
the original. The harness path keeps its old behaviour.

**Test:** `stream::tests::a_rewrite_too_large_for_a_frame_never_sends_the_original`
- a synthetic frame with a 60 000-byte extra TLV around a short text:
outbound, the engine's 7000-byte container would not fit - nothing of it
leaves, the note says so; inbound, a padded container decrypting to 6000
bytes - neither the container nor the padding reaches the client.

## 5. Call media before the call modules are patched

**Verdict: confirmed (a race).** `gate::media` (`gate.rs` 458) let a call
that must be encrypted through while the call modules were
`MediaHooks::NotLoaded`. `sipXtapi.dll` and `sipXmediaLib.dll` load with the
first call; when the loader notification came before their imports were
bound, `hook_calls::retry_later` patched them from a thread polling every
50 ms, while the module's own code could already run. Besides,
`Gate::media` counted both modules ready as soon as one was, and a module
unloaded after a call and loaded again for the next was unpatched again
until the notification caught it. The first RTP of a strict call could leave
unencrypted.

**Fix (preload).**

- `hook_calls::preload`: with `calls_encrypt` on, the bootstrap thread
  (outside the loader lock) loads both modules by full path from the
  client's folder (`LoadLibraryExW`, `LOAD_WITH_ALTERED_SEARCH_PATH`) and
  patches each as soon as it is loaded (`on_load`, two phases as before).
  The reference is never given back, so they are never unloaded and loaded
  unpatched again. A module the client lacks is `MediaHooks::Absent` (6.5
  has no `sipXmediaLib.dll`); one that cannot be loaded is `Failed`, as one
  that cannot be patched.
- The bootstrap now runs this before it settles the gate, so every module
  the client has is `Ready` before any connection is let through, and so
  before any call.
- `Gate::media` (`gate::combine`): ready only when every module present is;
  not loaded while one is not patched yet; failed if one failed.
- `gate::media`: `NotLoaded`/`Absent` blocks a call that must be encrypted
  (`required`, `/e2e on`, verified) - its SIP is dropped both ways, so it is
  never set up - and lets another go as it is, with a note and no key
  exchange that would claim it encrypted, as for `Failed`.
- The media hooks cannot drop what they do not see, which is why preloading
  rather than dropping is the fix; once patched, a strict or `required`
  call's unagreed media is dropped as since the first audit (finding 8).

**Tests:**

- `gate::tests::the_call_modules_are_ready_only_when_every_one_present_is`
- `hook::calls_io::tests::the_call_modules_are_patched_before_a_strict_call_is_let_through`
  - the order (load 0, patch 0, load 1, patch 1, all before the gate lets a
  strict call through), 6.5 with one module absent, one patched and one not,
  one that cannot be loaded.
- `stream::tests::a_strict_call_waits_for_every_call_module_to_be_patched`
  - through the stream: a strict call's INVITE never set up while one module
  is unpatched, keyed once both are (or one is absent).
- The fault matrices `gate::tests::no_internal_failure_lets_protected_traffic_through`
  and `hook::fourth_review::no_internal_failure_lets_protected_traffic_out`

  call's INVITE never reaches the server end; an automatic contact's goes

**Limit.** Loading the call modules at start runs their `DllMain` and static
initialisers before the client would have; it needs the live check below.
With `calls_log` alone (no encryption) nothing is preloaded, as before.

as it came: neither `plain_in`'s drop nor its unmark ever saw it. Besides,
with `e2e=off` (`Disabled`) the inbound branch of the same match returned

**Fix.** The inbound decision is made once, on what the parser says:

- no armor, or armor that `container::parse` does not read: `plain_in` - the
  fifth audit's rule (protected: dropped with the warning; automatic: shown,
  unmarked), logged as "armored but not a container: taken as unencrypted
  text";
- armor that is a whole container of this version and scheme:
  `crypto.inbound` (new function `container_in`);
- a valid header of a version or scheme this build does not know: the
  unsupported note and a drop, as before;
- `e2e=off`: nothing is decrypted, so a container is text too and goes
  through `plain_in` (shown, unmarked).

Every other inbound early return was checked for the same pattern (a branch
that hands on the original frame for text the client shows): a payload that
is not a SNAC carries no message; the MOTD and the user's own info carry
none; "buddy arrived", the Locate reply and Feedbag events are finding 2;
direct-IM proposals are dropped (second audit); a message SNAC that does not
decode goes to `plain_in` (fifth audit). One more was found and closed in

now dropped. What remains: with `ICQE2E_NO_INJECT` (a diagnostic switch) an
inbound container the add-on removes stays in the stream as the armoured

## 2. Authorization events and other text in a contact's name

**Verdict: confirmed.** The server copies the contact's text into every
authorization event (`foodgroup/feedbag.go`): `RequestAuthorizeToHost` into
`FeedbagRequestAuthorizeToClient` {screen name, reason} (674) or the legacy
channel-4 request `nick FE first FE last FE email FE auth FE reason` (722);
`rejectContact` into `FeedbagRespondAuthorizeToClient` {screen name,
accepted, reason} (1058) or a channel-4 denial (1074);
`ForwardICQAuthEvents` the reason of a channel-4 event into the Feedbag
forms (1110, 1117, 1155); stored ones come back as ICQ offline messages of
the same types (`foodgroup/icq.go` 445-466). The add-on passed all of them:
`rewrite::shown_text` named only `SHOWN_TYPES` (plain, URL, contacts), and the
fifth audit's test asserted "ch4 authorization request: no words, passes".
None of these can be authenticated end to end - the server makes them, the
add-on cannot send them - so the event can only be kept or not, and its text
cannot be the contact's.

**Fix (`authz.rs`, new).**

- For a protected contact, the reason of `0x0013/0x0019` and `0x0013/0x001B`,
  and of channel-4 and offline messages of type `0x06`, `0x07` and `0x08`, is
  replaced by the add-on's words: `[ICQ E2E] Authorization request (reply)
  attributed to <uin> was not end-to-end authenticated, its text is not
  shown.` (`policy::auth_local_text`; ASCII, one period, since the server
  strips periods after the first for ICQ 5). The event stays where it was,
  so the client's request dialog and its answer work as before. A legacy
  request keeps its first five fields (the server's copy of the requester's
  directory entry) and only its reason is replaced. An empty reason of a
  reply (a grant) stays empty.
- For any other contact, a reason that starts like a note of the add-on's is
  unmarked (`(from <uin>)`), in all those forms.
- Profiles, away messages and status texts are what a contact set for
  everyone, not words to the user; they are left as they are except that one
  starting like a note is unmarked: the Locate user info reply
  (`0x0002/0x0006`, TLV `0x0002` profile and `0x0004` away message, in the
  charset their MIME type names), the ICQ away message a contact's client
  sends back when asked (`0x0004/0x000B` on channel 2, types `0xE8`-`0xEC`),
  and the status text in the BART item of type `0x0002` of a contact's user
  info in "buddy arrived" and the Locate reply. An ordinary profile is not
  touched by a byte.

**Other carriers of a contact's free text, and what is done:**

## 3. A call or file proposal before an authenticated offer

**Verdict: confirmed.** An incoming INVITE (ICBM channel 6) went to
`CallTable::sip`, which made the call `State::Invited(None)` when no key
offer had come (`callneg.rs` 651), and the frame went on to the client
(`stream.rs` 547); only the media of a strict contact was blocked later. A
file proposal likewise: `FileTable::answer` took no offer as "plain"
(`filesneg.rs` 661) and the proposal reached the client (`stream.rs` 599);
`answer()` blocked a strict contact's transfer only once its connections
opened. So the server could ring the user, or offer a file, in a verified
contact's name, and the client showed it as theirs.

**Fix.** Both offers (`IQC1`, `IQF1`) are sent by the caller's or sender's
add-on over the Olm session before the signalling, on the same connection.
With `calls_encrypt` / `files_encrypt` on and frames that may be added and
removed:

- an incoming INVITE for a call not known yet, or a file proposal for a
  transfer not known yet, from a protected contact goes to the client only
  when `Crypto::authenticated` vouches for it: the offer for that Call-ID or
  cookie, from that contact, is waiting in the call or file table
  (`CallTable::vouched`, `FileTable::vouched`), or the call or transfer is
  one already set up (a re-INVITE, a counter-proposal to ours). The check
  spends nothing: the INVITE or proposal takes its offer as before;
- otherwise the frame is held (`StreamRewriter::hold`) for up to
  `HOLD_SECS` (3 s) and let through right after the frame that brought the
  offer (`settle_held`, after every inbound frame - keep-alives included -
  and every time the client sends, through `put_notes`);
- if none comes, it is dropped (`give_up`): the chat gets `WARNING: A call
  (A file transfer) in <uin>'s name was not put through (was not shown): it
  came without the announcement <uin>'s add-on sends over the encrypted
  session first ...` (`policy::unauthenticated_action_note`), at most once a
  minute per contact and kind, and the security box says it
  (`Crypto::unauthenticated`); and the sender is answered so their client
  does not wait: a `SIP/2.0 603 Decline` built from the INVITE's Via, From,
  To (with a tag of ours), Call-ID and CSeq (`callneg::decline_to_host`), or
  a rendezvous cancel of the cookie (`files::cancel_to_host`), queued in the
  socket's `Answers` (`owe_out`) and sent by the outbound direction with the
  client's next frame;
- the gate's refusal (fourth review) still comes first: a call or transfer
  it blocks is refused as before;
- an automatic contact's call and proposal: unchanged.

## 4. tZers

**Verdict: confirmed, two parts.**

- *Accepted by form.* The fifth audit let a tZer in a protected contact's
  name through when it had exactly the form the server writes
  (`rewrite.rs` 746, `tzer::is_served_tzer`), and a channel-2 plugin tZer
  (ICQ 6.5's own form) was never looked at. The server could therefore show
  "<contact> sent you a tZer", with a caption of its choosing, in a verified
  contact's name.
- *7.2 to 6.5 with encryption on was broken.* ICQ 7.2 sends a tZer as a
  channel-1 IM whose text fragment is the document and which carries the
  tZer mark (fragment `0x10`, `CapICQTZers`). The add-on decoded it as a
  message and encrypted it (`rewrite.rs` 527): the document became the
  armoured container and the mark stayed. The server's `parseTzerIM` still
  saw a tZer, took the armour for its document and, for ICQ 6.5
  (`tzerForRecipient`, `form == tzerIM && !tzerInIM`), wrote the plugin form
  around it: 6.5 got a tZer whose document was `IQE1:...`, which plays
  nothing, and its add-on never decrypted it (a plugin message is not text).
  For a contact under `/e2e on` with no session the tZer was held as a
  message instead. Between two 7.2 the tZer went encrypted and worked; 6.5 to
  7.2 worked because 6.5's plugin form was never encrypted.

**Fix (`tzer.rs`).** A tZer is a public animation, not a secret; what must
be protected is whose it is.

- *Out.* A tZer of either client - channel 1 with the mark
  (`tzer::ch1_doc`), or the channel-2 plugin message read the way the server
  reads it (`tzer::plugin_doc`, mirroring `parseTzerPlugin`) - whose document
  is one of this server's (`tzer::served_doc`, the fifth audit's check, now
  on the way out too) goes on exactly as the client wrote it, never through
  the message path. Before it, the add-on sends the contact an Olm control
  message `IQT1 | 1 | hash` (`tzer::Notice`, `Crypto::tzer_notice`), the hash
  being SHA-256 of the document without a trailing CRLF, cut to 16 bytes
  (`tzer::doc_hash`): the server copies the document unchanged through
  either translation, so both forms hash alike. A "tZer" whose document is
  not one of this server's is text and is encrypted as before.
- *In.* A tZer from a protected contact, in either form, is shown only when
  its document is one of this server's and a notice with its hash came from
  that contact within `tzer::NOTICE_TTL` (120 s); each notice vouches for one
  tZer (`authenticated` with `consume`). Not there yet: held up to
  `HOLD_SECS` for it, then dropped with the warning; not one of this
  server's: dropped at once. With `ICQE2E_NO_INJECT` a channel-1 tZer keeps
  its frame with the add-on's words, a channel-2 one becomes a cancel. From
  an automatic contact: as it came.
- The engine keeps the notices (`Engine::tzer_notices`, at most
  `MAX_NOTICES`); an older add-on takes an `IQT1` as an ordinary control
  message and shows nothing.

**The server's translation in the tests.** `core/tests/fixtures/tzer_forms.txt`
holds four forms generated from the server's own code (a throwaway Go test

7.2's channel-1 tZer, ICQ 6.5's channel-2 tZer, what the server makes of the
7.2 one for 6.5, and of the 6.5 one for 7.2.

## Limits (sixth audit)

- **A protected contact without the announcements.** A call, a file or a
  tZer from a protected contact whose client has no add-on, an add-on older

  are since the fifth audit; `/e2e off` in the chat lets them through again.
  tZers between an updated add-on and an older one stop in the direction of
  the updated one.
- **Our own switches.** With `calls_encrypt` / `files_encrypt` off the
  add-on keeps no offers, so it cannot tell an announced call or proposal
  from another; calls and files are then outside end-to-end protection
  altogether and pass as before. The same with `ICQE2E_NO_INJECT`, which
  never removes frames.
- **Timing.** A held frame is decided when the next frame passes either way
  (a keep-alive included) or the client sends; there is no timer of its own.
  The refusal to the sender goes with the client's next frame on that
  connection. Seconds are whole, so the window is 3 to 4 s.

  contact's text: the event itself (that someone asks, or answers) is still

- **Offline tZers** reach the client as the server's text "tZer: <name>"

  protected contact (as in the fifth audit).

# Seventh audit: binding, freshness and replay of announcements

An independent pass, of commit `04d1b72`, looked at what the sixth audit's
announcements (`IQC1` call offers, `IQF1` file offers, `IQT1` tZer notices)
actually vouch for. Threat model: the server may delay, reorder, duplicate,
suppress and change the legacy signalling (SIP on ICBM channel 6, rendezvous
proposals, tZer frames); it cannot forge Olm messages, account or device
keys. The question: can a genuine, authenticated announcement be combined
with changed, delayed or reused legacy signalling so that the client takes
it as a genuine action of a protected contact? Line numbers are those of
`04d1b72`. The documented compatibility modes (automatic contacts, `/e2e
off`, switches off, `ICQE2E_NO_INJECT`) are not counted.

The rule the code now follows: **an authenticated action is the contact +
the action's id (Call-ID, cookie) + a canonical digest of the signalling the
client will act on + a fresh time written by the sender - never "the contact
and the id are in a table".** Each action was checked for authenticity,
binding, freshness and single use; what failed is below.

| # | Finding | Verdict | Impact class |
|---|---------|---------|--------------|
| 1 | A call offer vouches for any INVITE with its Call-ID, whatever its SDP | confirmed (medium) | authenticity, privacy |
| 2 | Announcements have no freshness: the server can hold one for 14 days | confirmed (medium) | authenticity |
| 3 | A finished or refused Call-ID or cookie still vouches | confirmed (high for strict calls) | authenticity, confidentiality |
| 4 | An unauthenticated BYE, CANCEL or error answer turns an encrypted call plain | confirmed (high) | confidentiality |
| 5 | A file offer vouches for any proposal with its cookie | confirmed (medium) | authenticity, privacy |
| 6 | The 200 OK of an encrypted call is not bound to the callee's key answer | confirmed (low) | privacy, availability |
| 7 | A tZer notice binds only the document, not the rest of the frame | confirmed in the add-on (low) | authenticity |

## What the server legitimately changes

Canonicalisation must ignore exactly that and nothing more.
`foodgroup/icbm.go`: SIP on channel 6 is relayed as it is (173-179: only
logged), so an SDP is hashed as it comes - the same `callneg::sdp_hash` both
add-ons already used for the offer and the answer. A rendezvous proposal goes
through `addExternalIP` (451-480): the requester address `0x0003` is replaced
by the address the server sees (unless both clients share a network) and the
verified address `0x0004` is appended; nothing else in the rendezvous data
changes. The ICBM-level TLVs it strips (`0x0003` ack request, store, send
time) are outside the rendezvous data. tZers are rebuilt between the two
forms (`foodgroup/icbm_tzer.go`), with the document copied unchanged.

## 1. A call offer vouches for any INVITE with its Call-ID

**Verdict: confirmed.** `Crypto::authenticated(Action::Call)` (`crypto.rs`
2515) asked `CallTable::vouched(peer, call_id)` (`callneg.rs` 965-970), true
for a pending offer or any call with that Call-ID and contact. The SDP hash
the authenticated `IQC1` Offer carries was never compared with the INVITE:
`sip()` (703-723) took the offer for the INVITE whatever its SDP, and
`callee_answers` (803-924) answered with keys. The only comparison (941) is
on the caller, of the 200 OK against the callee's answer, after the 200 OK
has gone to the client, and only logs. **The owner's case, before the fix**
(probe run on `04d1b72` through two real engines: Offer for Call-ID `X` with
SDP H1, then a legacy INVITE `X` with SDP H2): `authenticated` = **true**;
the table logged `INVITE in, with a key offer`, the state went `invited`,
and at the 200 OK `answered; key answer sent first; media keys in use` - one
key answer sent. A server could so deliver a genuine call with addresses,
ports, codecs and ICE candidates of its choosing (the callee's client sends
its media, encrypted, and its address checks wherever the server says).

**Fix.** `Action::Call` carries the INVITE's SDP hash
(`callneg::invite_binding`); `vouched(peer, call_id, sdp, now)`:

- a call not set up yet: the pending offer must be from that contact, bind
  this SDP hash, and be fresh (2) (`PendingOffer::vouches`);
- a call set up and not ended: the SDP its offer bound (a retransmission of
  that INVITE), or one the peer's add-on announced for a re-INVITE, fresh;
- `callee_invited` (new) takes the offer only on the same conditions, also
  for an automatic contact (which is not held): an offer for another SDP is
  spent and the call goes on without keys (`another SDP than this INVITE
  carries: not taken`). A late offer (`Invited(None)`) is taken only when it
  binds the SDP of the INVITE that came.
- **Re-INVITEs** are announced: an outbound INVITE on a live call with
  another SDP than the last one this side announced is preceded by `IQC1`
  type 5 `Update {call, sdp}`. An add-on before this one decodes no type 5
  and takes it as an ordinary control message.

## 2. Announcements have no freshness

**Verdict: confirmed.** `PendingOffer.at` (`callneg.rs` 520-524,
`filesneg.rs` 372-380) and the tZer notices (`crypto.rs` 2304-2309) were
stamped with the local time of arrival; `OFFER_TTL_MS` and `NOTICE_TTL`
counted from there. The time the sender wrote the message is in the Olm
envelope (`container::Envelope::time`, authenticated, `keys.rs` 942), but
`OwnKeys::decrypt` checked it only against `TIME_SKEW_PAST` = 14 days (for
offline messages, 1056-1057) and dropped it. Olm refuses a replay of the same
message, and messages may arrive out of order (skipped message keys), so a
server could suppress a genuine `IQC1` + INVITE, `IQF1` + proposal or `IQT1`
+ tZer and deliver them up to 14 days later as a fresh call, file offer or
tZer from the contact.

**Fix.** `OwnKeys::last_sent_at` keeps the envelope time of the message
`decrypt` opened; the engine passes it as `sent` to `CallTable::control`,
`FileTable::control` and the tZer notices. One rule,
`crypto::announcement_fresh(sent, now)`: less than `ANNOUNCE_MAX_AGE` = 120
s old and at most `ANNOUNCE_MAX_AHEAD` = 60 s ahead by the sender's clock. It
is checked when the announcement arrives (stale: logged and ignored) and
again when the action is vouched for, so an announcement in time with its
action presented late vouches for nothing either. The tZer notices are kept
and matched by the sender's time (`tzer::NOTICE_TTL` is now that window).
The engine's file paths use the engine's clock like the call paths
(`file_icbm`, `control`: `now * 1000` instead of `filesneg::now_ms()`; equal
in the client, testable in the tests). No version change was needed: every
add-on has always written the envelope time.

## 3. A finished or refused Call-ID or cookie still vouches

**Verdict: confirmed.** `vouched` was true for any call in the table, also
`State::Ended` during `ENDED_GRACE_MS` (10 s, `callneg.rs` 1171-1191). An
INVITE with an ended call's Call-ID - the genuine one again, or any - was
let through within those 10 s (probe on `04d1b72`: `vouched` true after a
BYE); `sip()` ignores an INVITE for a known Call-ID (704), so the client
rang in the protected contact's name with no key exchange, ran its "new"
call on the ended call's keys and, once they were forgotten, unencrypted
(the strict hold, `blocks_plain` 1214-1219, ignored ended calls). Files the
same: a cancelled transfer vouched for any proposal with its cookie for
`ENDED_GRACE_MS` (30 s, `filesneg.rs` 935-943, 753-757), and a live one for
every later proposal. And an INVITE held and given up (the 603 sent) could
be vouched for later by its offer, which the server let through afterwards.

**Fix.** `CallTable::burned` / `FileTable::burned`: the Call-ID or cookie of
every call or transfer that ends (`end`) and of every action given up
(`Crypto::refused`, new, called by `StreamRewriter::give_up` →
`CallTable::refuse`, `FileTable::refuse`), kept `BURN_KEEP_MS` = 10 min (far
past any fresh announcement), at most 256. A burned id is never vouched for
and an offer for it is ignored; an ended call or transfer vouches for
nothing.

## 4. An unauthenticated BYE, CANCEL or error answer turns an encrypted call plain

**Verdict: confirmed.** `sip()` (734-739) ended a call on any BYE, CANCEL or
final error answer to the INVITE, in either direction; inbound ones are
legacy signalling the server can make. The add-on matches only the Call-ID,
the client matches tags, branch and transaction: a BYE with other tags gets
481 and the call goes on; a final answer after the 200 OK is a stray the
client drops. The add-on kept the keys 10 s and forgot the call; from then
on the media hooks passed every datagram as it is (`hook_calls.rs` 334: no
keyed call and no strict hold). Probe on `04d1b72` (agreed call, a strict
contact, a forged inbound BYE at the caller): state `ended`; media still
encrypted during the 10 s; after them `media_out` = **Pass** (plain RTP) and
`blocks_plain` = false. Before keys the same: a forged CANCEL forgot a strict
contact's ringing call, the client answered anyway, the 200 OK found no call
(`callee_answers` 811), no key exchange, and the media went plain.

**Fix.**

- `end_from`: an end from our own client (outbound) is authentic and ends at
  once, as before. An inbound one on a call with keys only sets `end_req`;
  the keys stay while the call's media goes on (`last_media`, updated by
  `media_out`/`media_in`), and the end takes effect once there has been no
  media for `ENDED_GRACE_MS` after it, or when our client accepts it (its
  2xx to that BYE or CANCEL). Then the usual grace.
- An inbound end of a call without keys keeps it as ended for the grace, and
  `blocks_plain` counts such a strict call too.
- `unseen_call`: a 2xx to an INVITE (either way) for a call with no live
  set-up - never seen, or ended without keys - makes it a call without keys
  through `go_plain`: dropped media for a strict contact, plain with a note
  for an automatic one. Never "unknown, so as it is".

## 5. A file offer vouches for any proposal with its cookie

**Verdict: confirmed.** `FileTable::vouched(peer, cookie)` (`filesneg.rs`
753-757); `IQF1` carried no digest of the proposal. The server could keep
the cookie and change, after a genuine `IQF1`: the file name, count and
size (service data `0x2711`) and the invitation text (`0x000C`) - shown in
the accept dialog in the protected contact's name; the proposed address
(`0x0002`), port, proxy flag (`0x0010`) and stage (`0x000A`) - where the
receiving client connects (IP disclosure, connects to an address of the
server's choosing). Counter-proposals (reverse, proxy stage) were never
announced at all; any one with a known cookie was vouched for. Consequences
checked separately: no plaintext leak - a keyed transfer's every connection
needs the peer's MAC'd key hello (`filestream.rs`), which the server cannot
make; spoofed displayed metadata - yes; IP disclosure and connects to an
arbitrary address - yes; denial of service - yes.

**Fix.**

- `files::rdv_digest`, `Rendezvous::digest`: SHA-256 (16 bytes) over the
  type, cookie, capability and every TLV of the rendezvous data but
  `0x0003` and `0x0004` (the two the server rewrites), sorted by tag, each as
  tag, length, value.
- `IQF1` Offer carries the digest after the suites (`Msg::Offer::digest`).
  Old decoders leave bytes after the known fields alone; an offer from an
  old add-on reads with `digest: None`.
- Every later outbound proposal of a known transfer is preceded by `IQF1`
  type 4 `Proposal {cookie, digest}` (an old add-on takes it as an ordinary
  control message).
- `vouched(peer, cookie, digest, now)`: an unknown transfer - the pending
  offer binds this digest and is fresh; a known one not ended - the peer
  announced this digest, freshly; a burned cookie - never. `answer` takes the
  offer only when it is fresh and its digest matches (or it has none: an
  older add-on, which reaches `answer` only for an automatic contact).

**Limit.** The verified address `0x0004` and the requester address `0x0003`
are the server's to set (NAT), and a client may connect to them: the server
can still steer where the receiving client connects through those two. The
data stays encrypted (the key hello), so it is IP disclosure or denial of
service, not a leak.

## 6. The 200 OK of an encrypted call is not bound to the key answer

**Verdict: confirmed (low).** The callee's key answer carries the hash of
its 200 OK's SDP; the caller compared it (`caller_sees_ok` 940-947) only to
log `WARNING the SDP of the 200 OK is not the one the callee's add-on saw;
the media stays encrypted` - after the frame had gone to the client. The
server could redirect the caller's (encrypted) media.

**Fix.** `Action::CallAnswer {peer, call_id, sdp}` for an inbound 2xx to an
INVITE (`callneg::answer_binding`), asked by the stream for a protected
contact like the INVITE; `CallTable::answer_vouched`: a call with agreed keys
needs the SDP the key answer bound, any other call binds nothing here (it is
plain or refused by its own rule). Not vouched for: held and dropped with
the warning ("An answer to your call in X's name was not put through"); no
603 goes back for an answer.

## 7. A tZer notice binds only the document

**Verdict: confirmed in the add-on (low).** `tzer_of` / `tzer_in`
(`rewrite.rs` 998-1015, 1045) took the document from the first text
fragment (`tzer::ch1_doc`) or the plugin service data (`tzer::plugin_doc`)
and checked it and its notice; the rest of the frame was not looked at. A
channel-1 tZer could carry a second text fragment, a channel-2 one a text in
the plugin message (ICQ 6.5 writes it empty) or an invitation TLV beside it,
and still match the notice. Whether ICQ 6.5 or 7.2 show such extra text was
not checked live; the add-on vouched for content it had not authenticated.

**Fix.** `tzer::ch1_exact` (exactly the three fragments features, tZer mark,
text, in that order) and `tzer::plugin_exact` (only the TLVs `0x000A`,
`0x000F`, `0x2711`, an empty plugin message text, nothing after the
document; the headers' sequence numbers and flags are the sender client's
and are not looked at). From a protected contact a tZer must be exact as
well as one of this server's and announced; otherwise it is dropped as not
one of this server's tZers. Both clients' own forms and the server's
translations (`core/tests/fixtures/tzer_forms.txt`) are exact.

## Checked, no finding

- **A duplicated `IQT1`** opens once: Olm refuses the second copy (its
  message key is spent), so one notice vouches for one tZer
  (`a_duplicated_tzer_notice_vouches_for_one_tzer`, a guard: true before).
  Several genuine notices of the same document vouch for as many tZers as
  were sent - within the window now.
- **Exactly-once consumption**: `settle_held` asks without consuming and
  `tzer_in` consumes when the frame goes on; a second held copy is given up.
- **Inbound 180, ACK, INFO and other SIP** decide nothing in the table.
- **A forged file cancel** ends the transfer in the client too: denial of
  service only.

## Compatibility with older add-ons

- **Calls**: an older add-on's `IQC1` Offer always carried the SDP hash, and
  every add-on has written the envelope time, so calls from older add-ons are
  vouched for as before. An older add-on's re-INVITE with another SDP is not
  announced: from a protected contact it is dropped (603). Our `Update` is an
  ordinary control message to it.
- **Files**: an older add-on's `IQF1` has no digest and it never announces a
  counter-proposal: its proposals in a protected contact's name (seen
  encrypting counts) are no longer shown - dropped after 3 s with the
  warning, the sender's client told no. An automatic contact's proposal still
  takes the offer and is encrypted. Update both sides.
- **tZers**: the protocol is unchanged; a frame that is not exact was never
  written by either client.
- **Clocks**: an announcement written more than 60 s ahead of the receiver's
  clock, or presented 120 s or more after it was written, is refused (logged
  `stale`). Two computers whose clocks are more than about a minute apart
  lose calls, files and tZers in the direction of the one behind; keep
  Windows time synchronisation on.

## Limits (seventh audit)

- Within the 2-minute window the server can still delay a genuine action
  (hold an `IQC1` and its INVITE, then deliver both), or present a
  retransmission of the INVITE its offer bound while the call lives.
- A call ended by the network keeps its keys as long as media flows; a
  client that really hung up but keeps sending media for a moment is
  covered by the same grace as before.
- A strict call without keys ended by the network holds back unagreed media
  for its 10 s of grace, also that of a call with an automatic contact
  started within them.
- Item 5's limit: `0x0003`/`0x0004` stay the server's.
